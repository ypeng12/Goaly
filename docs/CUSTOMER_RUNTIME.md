# 客户对话、RL 与项目的验收目标

保险理赔是演示场景。这个项目展示的是：把受业务规则约束的客服问题变成可训练、可检查的 Agent 系统，并把训练出的动作策略用于客户实际输入的对话。

## Agent 要做到什么

客户可以用自己的表达咨询，不必按题库走。合格结果需要同时满足这些条件：

| 客户遇到的情况 | 应得到的结果 | 不能算成功的情况 |
|---|---|---|
| 不知道 claim 是什么 | 简短解释与可选咨询方向，仍可直接打字 | 只展示技术术语或强迫先填写全部表格 |
| 一开始就说了拒赔、月份 | 验证期间记住线索，三项核对后继续处理同一诉求 | 提前展示案件，或通过后重新问一遍来意 |
| 只填写姓名，或者姓名加生日 | 显示 1/3 或 2/3，继续索取缺项；案件保持锁定 | 把一条成功聊天回复当成验证已经通过 |
| 问“第二份是什么”“拿不到它怎么办” | 指向上一轮实际展示的材料；有歧义时澄清 | 每次重复整个案件，或者猜测不存在的材料 |
| 问照片、扫描、期限 | 根据记录说明接受条件；记录没确认则明确说需确认 | 为了自然流畅而承诺未知格式、批准或新的期限 |
| 生气或担心 | 选择安抚并继续提供有效帮助，不能绕过身份门禁 | 只说安抚套话，或者不理会持续的担忧 |
| 仍有问题 | 继续回答；不因回答过一次就结束 | 为减少轮数提前推邮件或转人工 |
| 已问完 | 提供摘要并让客户选择发送或跳过 | 没有明确同意就发送；把“可能晚些”当成同意 |

## 一轮真实对话怎样处理

1. **理解当前原话及受限上下文。** 本轮原话进入 SOP。服务器仅从当前已验证案件的真实历史展示中解析材料序号、指代和主题；不会把旧聊天重新当成身份信息或 consent。
2. **SOP 决定权限。** 身份至少三项匹配、案件归属、阶段顺序和发送同意由代码核验。理解模块和策略不能解除这些限制。
3. **PPO 选择允许的动作。** 在可以选择时，训练权重决定是简短询问信息、解释验证目的、安抚后推进、澄清或回答。只有一个合法动作的回合标记为 forced；不能把这种必选动作当成学习能力证据。
4. **执行被选择的动作。** ASK 实际询问缺项；ACK 实际加入安抚；ANSWER 实际调用有权限的事实回答；允许的人工升级实际改变 SOP 状态。不会把 Agent 动作翻译成虚构的客户话术。
5. **客户继续回复。** 真实聊天由人回答；训练时使用读取实际 Agent 回复的 ReactiveCustomer。每轮保存实际消息、状态与策略记录，可还原上下文和策略记忆。

明确要求人工、跑题处理、已作出的邮件选择及结束确认，由 SOP 直接执行，记录 `source=sop`、空策略动作与空权重标识。客户请求可以立即转人工，模型不能声称这是它学会的决策。

## RL 用在哪里，语言模型用在哪里

| 部件 | 学习或负责的内容 | 不负责的内容 |
|---|---|---|
| Masked PPO | 30 维可观察特征到 9 个对话动作；在 mask 允许的选项中选择 | 不训练大语言模型，不生成理赔事实，不决定验证通过 |
| Caller simulator | 依据实际回复提供身份、追问、拒绝或邮件选择 | 不读取策略动作标签、未来状态、模型分数来配合成功 |
| 语言理解模型（配置 token 时） | 较宽的表达、主题、情绪、已展示材料的受控索引 | 不访问未验证案件，不给历史话术重新授权，不执行发送 |
| 回答规划模型（配置 token 时） | 排列已批准的完整事实块，选择段落或步骤布局 | 不能改写事实、遗漏条件或自由补充记录里没有的答案 |
| 确定性上下文与 composer | 无 token 时也可完成已覆盖的连续追问与准确回答 | 有限语法不等于已验证任意自然语言泛化能力 |

因此，部分合规说明与事实句仍有固定措辞。优化的是理解连续对话、选择当前真正需要的内容以及采取合适动作。不能把界面支持自由输入，说成已经证明了所有自由表达都能正确理解。

## 在页面上看什么

客户页输入框优先展示；建议问题可以展开。Settings 中 **语言引擎** 与 **动作控制器** 分开选择。每轮的 **This response** 展示实际执行源、动作、合法动作概率、权重版本和回退原因。概率是动作偏好，不是答案正确率。

Developer lab 先展示当前客户策略的对比，再提供原始版本 3 的模拟器实验。客户版本 4 使用独立权重和当前对话执行器；相同 seed 名字不表示两边是同一个模型。只在相同环境、场景和执行器下比较结果。

判断好坏的顺序是：**没有越权 → 回答对了并达到合理结果 → 再比较少重复、安抚和轮数**。奖励是为训练设计的分数，不是满意度。转人工应单独统计，不应算作案件完成。

## 训练与可复核证据

客户训练的独立入口为 `train_customer_policy.py`。版本 4 环境复用实际客户的 mask 与 executor，增加多次材料追问、情绪持续时的反应和明确邮件选择。奖励根据真实话术与状态结果计分：完成问题及 consent 获得完成奖励，忽略情绪、无必要重复隐私解释、超时和违规被扣分。

[当前对比报告](../artifacts/customer_policy/comparison.json) 在同一当前执行器中比较规则、原始两个 PPO 权重与新训练的两个权重。它保留各场景的完整交互、模型 SHA、实际训练步数和指标。Caller 使用有限关键词协议判断是否继续；该协议的“收到回答”不能代替事实准确性检验，后者由 API 与浏览器的材料、期限、原件条件断言补充。语言逻辑的修复对所有策略共同生效，不能把它归功于 PPO。

```bash
# 当前分布的全新训练；交付权重的三段续训历史见 artifacts/customer_policy/README.md。
OMP_NUM_THREADS=1 MKL_NUM_THREADS=1 python3 train_customer_policy.py --timesteps 60000 --seed 42
OMP_NUM_THREADS=1 MKL_NUM_THREADS=1 python3 train_customer_policy.py --timesteps 60000 --seed 7
OMP_NUM_THREADS=1 python3 -m eval.customer_policy_comparison --assert-thresholds
python3 -m pytest -q
python3 -m eval.eval_benchmark
# 先启动服务；安装 Playwright 后运行：
python3 -m eval.browser_acceptance --require-customer-report
# 配置真实 token 后运行，缺 token 返回 not_run：
python3 -m eval.live_acceptance
```

两 seed 是稳定性检查，有限的合成 caller 不代表真实人群。评测表达没有进入训练采样，但开发中已用来排查共用的语言理解问题，因此这里是开发评测，不是完全未接触的独立盲测。零违规说明测试下 SOP/mask 生效，不能证明 PPO 自己学会了安全。DPO 文件是偏好数据，并未训练 DPO 语言模型。真实模型验收只有实际 provider 请求成功且所需回答规划成功才能通过；离线正确回复或 provider fallback 不冒充成功。

## 本次测得的结果

两个 seed 各累计 60,288 步，保留 20k、40k 阶段失败记录并补充情绪与缺信息的训练场景。在相同执行器的 7 个开发评测场景中：

| 指标 | 原 PPO（两个 seed） | 新 PPO（两个 seed） | 规则基线 |
|---|---:|---:|---:|
| 完成案件及邮件选择 | 3/7 | 6/7 | 6/7 |
| 预期无匹配案件转人工 | 1/7 | 1/7 | 1/7 |
| 未解决就转人工 | 2/7 | 0/7 | 0/7 |
| 超时 | 1/7 | 0/7 | 0/7 |
| 忽略评测中的明确担忧/愤怒 | 87.5% | 0% | 0% |
| 观测到的规则违规 | 0 | 0 | 0 |

新策略在这组场景中达到规则基线的业务结果。它没有被证明比规则更高效：两者平均策略步骤相同，新 PPO 的最终确认话术反而略多。主要收获是让学出的策略适应真正的多轮执行流程，并通过独立检查发现并修复了训练覆盖缺口。

当前本地全套测试为 292 passed；原 SOP 基准为 33/33 场景、650/650 断言。真实 provider 没有配置 token，因此是 not_run，不能把模拟 HTTP 的通过称为真实模型通过。
